# DSH 对话机制研究（孪生重设计地基，2026-10-01）

目的：回应三个痛点——**监察成功率低、烧 token、缓存命中率低**——先把宿主「一轮对话」的完整机制从源码摸清，再对照孪生现行实现给出机制级归因与重设计杠杆。全部结论带源码出处（行号为 2026-10-01 当日版本）。

---

## 1. 一轮对话的完整生命周期（`dsh-agent-loop/lib/index.js`，1981 行）

```
followup(input) ──► inbox ──► wakeDriver() ──► kick() = while(await turn())
turn():   session.append('turn/start') → 循环 step
preStep:  inbox.claim(本轮新输入)
          → systemPrompt.assemble(assembleContextFor(agent))   // 段落+上下文+变量求值（{{model}} 在这里解析）
          → renderContextSections + runtimeContext.project     // 运行时上下文快照
          → 瀑布 agent/pre-step { messages: claimed }           // ★ 孪生的文本闸挂这里
          → 默认 enter: messages = [...claimed, runtimeContext]
step():   renderPrompt(assembly)                                // 系统提示渲染（变量插值在 dsh-system-prompt:172，缺值即抛）
          → prepareRequest: 瀑布 agent/request 改写 config      // provider/model 缺失即抛（{{model}} 事故的近亲）
          → llm.prepareCall(config)                             // 绑定 adapter：contextWindow/systemPromptUpdate/retryPolicy
          → systemPrompt.project(renderedPrompt, {inHistory, startsSeries, toolsChanged})  // ★ 见 §2
          → decision.messages 逐条落 user/message
          → buildRequest: request/header（initial/resume/change/series）→ deriveMessages() 冻结为 messages
          → (preparedCall?.stream ?? llm.stream)(request)       // ★ 孪生的监察调用走的是同一个 llm 服务
          → assistant/message（含 usage）落盘 → tool-call → executeToolCalls（内部 tools/pre-execute 瀑布 ★ 工具闸挂这里）
          → 有 tool-call 回到下一 step；无 → completed
```

关键结论：**发给模型的消息 = 会话日志的派生消息面（`session.deriveMessages()`）**；系统提示以 `system/message` 事件**只在变化时**提交进日志；工具集变化会追加 `developer/message`（tool-addition/removal）。

## 2. 缓存机制：宿主本身就是缓存感知的（三条源码证据）

1. **`request/header` = 缓存身份**（agent-loop L1202-1228）：`config + adapterDefaults + tools` 组成 header，只在 initial/resume/**change**/series 时记录；`toolsChanged()`（L926-934）专门对比工具集是否相对已记录 header 变化——变了就强制重提交系统提示（= 主动声明"缓存失效点"）。工具增删还会落 `developer/message` 告知模型。
2. **压缩插件就是"暖前缀 sidecar"的官方范例**（`dsh-compaction-basic` L236-242 原文）：
   > 把压缩指令作为**最后一条 user 消息**、放在重放的对话后面，"Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call **a genuine prefix of the last routed request**, so **the provider's KV cache is reused** instead of invalidated."
   实现（L292-323）：`messages = [...input.messages, {role:'user', 指令}]`，目标模型优先取 **`agent.session.requestHeader()?.config`**（= 上一路请求的 config，缓存必然是热的），并**带上 `tools` 与 `toolHistory`** 保持请求形状一致，另传 `purpose:"compaction"`、`sessionId`。
3. **`dsh-llm` 对缓存的态度**（L350-354）：provider/model/reasoning effort 等是"request-header state that **can affect cache reuse**"——由 waterfall 统一替换并记录变更快照，**不允许逐调用静默漂移**。

**可量化**：usage 携带 `cacheReadTokens / cacheWriteTokens / uncachedInputTokens`（`dsh-token-meter` L340-351）——每次调用的缓存命中率可以直接读出来，重设计的 B 判据不用猜。

## 3. 孪生现行调用对照（三个痛点的机制归因）

现行默认（flatten 模式，`impl.mjs` L760-795）：

```js
base        = sanitizeForTwin(session.deriveMessages())   // 清洗：剔 system/plugin 消息、拍平、去标记
contextText = contextTextFor(base, cfg)                   // 最近 10 轮拍平成纯文本，≤24000 字，工具剔除
instruction = buildInstruction(45 条判据 + role + usage + contract + 教训 ≤2400 字 + 待审对象 + 用户原话 [+ prefill])
messages    = [userMessage(instruction)]                  // ← 单条巨大 user 消息
ctx.llm.stream({ provider, model, messages, signal })     // 无 tools / toolHistory / purpose / sessionId
```

| 痛点 | 机制归因 |
| --- | --- |
| **成功率低** | 冷启动单问形态：模型面对"一份巨大审查文档"而不是"对话的延续"；历史上有伪造尾消息事故（已默认关）；45 条判据诱发长思考 → 3.2 万 token 截断/只思考不答；5×5s 重试 + 与主会话抢并发 → 429 |
| **烧 token** | 每次审查的输入 = 24k 字转录 + ~6k 字判据/教训 ≈ 上万 token，**全部全新计费**；转录尾部逐次滚动，连"上次审查"之间也无复用 |
| **缓存 0%** | 结构性：flatten 是单条 user 消息，前缀逐次不同；即便切 'full' 模式，`sanitizeForTwin` 会**剔掉 system/plugin 消息并改写内容** → 与主会话请求的字节面前缀在第 0 条就分叉 → 永远不命中 |

## 4. 重设计杠杆（按证据强度排序）

**杠杆 A（推荐，官方压缩引擎同款）：共享前缀 sidecar**

```js
const cfg0 = agent.session.requestHeader()?.config          // 上一路请求的 config = 缓存热的路由
const messages = [...session.deriveMessages(),              // 原样重放（不清洗、含 system 提交）
                  { role:'user', content:[{ type:'text', text: monitorDirective }] }]  // 指令只放最后
ctx.llm.stream({ provider: cfg0.provider, model: cfg0.model, messages,
                 tools, toolHistory: session.toolHistory(), sessionId, signal })
```

- **为什么成立**：与压缩引擎完全同构，而压缩引擎在本机每天多次生产运行；被审动作时点恰好在 assistant 工具调用消息落盘之后 → 重放前缀的尾部**天然就是要审的那个调用**，模型带全上下文裁决（准确率的根本改善）。
- **收益**：输入大头按 cache-read 计价（usage 可量化验证）；不再重发 24k 字拍平文本；"续写式"形态替代冷启动单问 → 空回复/只思考类失败应大幅下降。
- **代价与待验证**：① `sanitizeForTwin` 的防欺骗清洗不能再整段做——折中方案是**前缀原样 + 仅对被审动作/尾部 k 条清洗**；② tools/toolHistory 是否必须随行（压缩引擎带了，照抄最稳）；③ `purpose` 字段 dsh-llm 源码未处理（压缩在传，容忍未知字段），语义待证；④ sidecar 与主会话抢并发（沿用现有全局串行 + 429 退避）。

**杠杆 B：审查降频**——规则前置（允许清单/路径/正则先放行明显合规动作），LLM 只审灰区；或按风险分级 + 抽样。直接砍调用次数。

**杠杆 C：判据瘦身**——45 条全量 → 按工具类型路由的小判据集（即使留在杠杆 A 里，指令也该从 ~6k 字瘦到 ~1k）。

**杠杆 D（备选）：事后抽查**——把"事前拦截"改为"事后从会话日志抽样取证 + 必要时 followup 注入纠正"，审查彻底离开关键路径。牺牲即时拦截，只适合低成本兜底。

**不推荐**：in-band 自审（pre-step 往主请求里塞审查指令、从回复里解析裁决）——污染执行侧行为、裁决与正文混流、且有会话写入纪律风险。

## 5. 量化对照（机制推算，非实测）

| | 现行 flatten | 杠杆 A（共享前缀 sidecar） |
| --- | --- | --- |
| 每次审查 input | ~1.5–2.5 万 token **全价新前缀** | 大头 = cache-read 价；新增 ≈ 指令+被审动作（~1–2k token） |
| 缓存命中 | 结构性 0% | 主体命中（可从 usage 直接量出） |
| 形态 | 冷启动单问 + 巨型文档 | 对话延续 + 末尾指令（生产验证过的形态） |
| 上下文保真 | 拍平 10 轮/24k 字、工具剔除 | 全量派生面（含工具往返与系统提交） |

## 6. 待验证清单（下一轮做）

1. `deriveMessages()` 字节稳定性：同 surface 下两次调用是否逐字节一致（fold 增量路径）；
2. tools/toolHistory 是否必须进 sidecar（缓存哈希是否含 tools——压缩引擎带了，先照抄）；
3. usage 里 cacheRead/Write/uncached 的实际值（探针直接量命中率，作为 B 判据）；
4. `purpose` 字段语义；
5. sidecar 与主会话并发的 429 策略（沿用全局串行 + 4×退避是否够）。
