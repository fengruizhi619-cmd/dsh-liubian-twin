# 孪生重设计 v3：「对话里的对话」（2026-10-01 管理员定案）

> 管理员原话：**「把事情简化成这样一个对话有两个上下文，不再复用一个上下文伪造后缀」**；
> 「**相当于在 DSH 中另起一个对话，但是这个对话放在原对话的对话里**」。
>
> 本文回答两件事：① 宿主可行性核查的结论与证据；② 在这个定案下 M2 的实施设计。
> v1（复用上下文+伪造后缀）就此退役；v2 M1（影子会话，`43f0b74`，未启用）被确认为正确宿主形态。

---

## 1. 可行性核查结论（2026-10-01，全部源码实证）

**现在的 DSH 放不下"一个会话两套对话系统"**——"一套对话所需的系统"与会话是 1:1 绑定的：

| 系统 | 事实 | 出处（`E:\DSH Desktop\resources\app\node_modules\@deepseek-ai\`） |
| --- | --- | --- |
| 模型可见面 | 每会话**唯一** `surfaceManager`；上下文 = 事件日志的派生面，surface 只有 `append`/`replacement` 两种 op | `dsh-session` L1324 / L145-199 |
| agent | 注册表 `Map` 按 sessionId **单映射** | `dsh-agent` L323 / L339 |
| 系统提示装配 | preStep 时按唯一 agent 装配 | `dsh-agent-loop` L902-925 |
| request/header（缓存身份） | **每会话一条链**，变化即强制重提交系统提示 | `dsh-agent-loop` L1202-1228 |
| 压缩检查点 | 按会话唯一 surface 工作 | `dsh-compaction-basic` L344-356 |

**官方旁证**：`dsh-experimental-auto-review`（宿主自带、与本插件完全同构的逐调用工具审查）也没做第二上下文——它每次从 `session.snapshotEvents()` + `session.requestHeader()` **重建"五分区"过滤视图**单发调用，明确排除主 agent 的 system 提交/assistant 正文/reasoning/tool results，且 README 自认 reviewer 调用"**不缓存**、重试、截断、压缩"。→ 宿主官方面对同一个问题，选的正是我们决定放弃的形态。

**为什么"硬塞进一个会话"更贵**：`request/header` 是每会话唯一缓存身份链，两个上下文交替请求 = 每次交替都是一次 header `change` = 强制重提交系统提示 = **两套上下文的 KV 缓存互踢**；压缩也只认唯一 surface。这些机制在 agent-loop/session 内部，插件瀑布上没有绕开的挂点。

**结论**：宿主全家所有"多上下文"功能（agent-team 的 teammates、subagent fork、被炉房间）都是同一拓扑——**多个会话 + 消息投递**。「一个对话两个上下文」的插件可行形态 = **UI 合一、存储两会话**：影子会话（独立 system prompt / header / 压缩）+ 把它渲染进主对话页签。这同时天然消灭伪造后缀——影子会话里审查指令是真实 user 消息。

## 2. 本轮新核查的三件事（设计输入）

### 2.1 侧栏可见性：**没有插件级隐藏机制**（设计上唯一要拍板的点）

- 会话列表 API `api-session-controller.list()`（L1888-1906）**不过滤** `origin`/`parentSession`：活会话必列（L1895-1898），冷会话仅在没有 `cwd` 时被跳过（L1900）。
- `sessionListMetadata`（含 `blank`）只在 `dsh-api-session-controller` 内部产生（L1789/1807/1838）；`dsh-session-projection` 的注册表**拒绝共享已注册 key**（L91），插件注册不进 `sessionListMetadata` 这条路。
- 白泽坑位①的"隐藏开关未找到"成立，且现在有了机制级解释。
- **唯一找到一个的杠杆（不推荐用）**：影子会话不给 `cwd` → 冷态从列表消失（L1900）。代价：活着的影子 agent 仍会被列（L1895），且 cwd 牵连工作区路由与 workspace 事件，属于为了美观引入行为风险的 hack。**不做。**
- **已拍板（管理员）**：接受侧栏条目存在，名称就叫 **「孪生」**（原提议的 `〔监察〕<标题前12字>` 规约作废）。将来若宿主提供 hidden 标志再跟进（不是我们能做主的）。

### 2.2 官方先例：日志可以持有"不进 surface"的事件（记录，不动手）

agent-team 的协作事件（`team/member`、`team/message/*`）**只进会话日志、从不进会话表面**（README.zh.md L147："派生模型历史不受协作记录影响"）。理论上监督台账可以住进主会话而不污染上下文——但这是宿主包带 invariant 校验的特权用法，**插件能否安全写入未验证**（主会话写入纪律是血案换来的：步外写入会弄坏压缩）。**不动手**，只记录为将来的探针方向。

### 2.3 M1 的既有实现与新定案的差距

M1（`43f0b74`）已实现影子会话全链：create（官方 createOrAdopt 形状 + agentOptions）→ bootstrap 照抄 → followup 投递 → 事件等待器 → 裁决解析，`twinV2` 默认关，桩测 51/51。**与 v3 定案的差距只有两块**：① UI（当时明确"待 M1 实测后做"）；② v1 路径的退役。架构本身零改动。

```

   │  页签：〔对话〕〔孪生 ← 新增〕〔轨迹〕

   · 自己的压缩（宿主压缩引擎对它照常生效）
   · bootstrap 照抄主对话一次，此后只收增量（M1 已实现）
```

## 7. 2026-10-03 事故与探针结果（首启实测）

**事故**：插件启用后页签出现，**重启后页签消失**。根因（宿主日志实锤，非推断）：
`mountTwinPanel` 访问 `ctx.webServer`，而孪生的 `main.mjs` inject 没声明 `webServer`
（v1 从不用它，M2 加面板时没对照入口清单）→ `cannot get property "webServer" without
inject` → **整个 apply 带死**。热挂载时页签之所以"在"，是因为 client 半独立于宿主
apply 注册——**"页签在"不是宿主半活着的证据**；重启后整包装配失败，client 半跟着没了。

**修复（v0.3.1）**：① `main.mjs` inject 补 `'webServer'`（正路，需重启生效）；②
`mountTwinPanel` 三层防御——`ctx.webServer` 的访问本身会抛所以先 try、reflect 直取兜底
（〈便签可视化栏实现要点〉记录的绕行）、整体 try/catch，**面板绝不连坐闸门**；③ 挂载
成功打一行 info 日志（`面板路由已挂载 /api/liubian-twin`）作验收判据；④ 静态护栏进
`verify_client_boot.mjs`（inject 四项缺一即红）。

**探针结果（F8 预登记判读表的首次真机实测，受试 = patch 重装配）**：
patch SHA-256 前后一致（内容零改动）→ 纯 mtime touch → 12 秒观察窗**零新日志**
（无 [hmr] reload、无 twin 重挂载）。**判读 = A✗：mtime-only touch 不触发重装配**，
按预登记第三行，纪律触发条件应为「**需要内容变更**」。此前全族口径"touch patch 即热更"
作废；本机 bundle 插件热更的两条实证路径 = **内容变更的 patch 编辑**（infra disabled 移除
那次）与**重启**。

**教训（进家族标准 §8 的候选）**：① 在 apply 里新用任何宿主服务，必须同步在 main.mjs
inject 声明——**声明清单是入口的契约，不是可选注释**；② 附属功能（面板/路由/UI）的挂载
必须自带 try/catch 与服务缺席降级，不能与承重路径（闸门）同生共死；③ 写完插件要过
`dsh-plugin-checklist`——本坑正是它管的"服务未声明/依赖未解析"类。

**第二击（v0.3.2）**：修完 ① 重启，宿主半全好（`面板路由已挂载` + `v0.3.1 已挂载`），
**页签仍然没了**——第二根因在 client 清单：`dsh.client.inject` 漏了
**`@deepseek-ai/dsh-client-runtime`**。`window.__ModuleLoader__` 正是 runtime 提供的；
冷启动时我的模块先于 runtime 求值 → 求值即死 → 页签消失。**热挂载时页面早被别的
client 把 runtime 带起来，所以"打开时有、重启后没"**——第二个"热好冷坏"形态。
对照样本：kotatsu 与 notes（冷启动一直正常）的 `dsh.client.inject` 都是
`["@deepseek-ai/dsh-client-runtime", "@deepseek-ai/dsh-client-ui-conversation"]` 双声明。
护栏已进 `verify_client_boot.mjs`（两个包名缺一即红）。

**两击合起来的教训（同一族）**：client 半有**两份依赖清单**——入口的 `inject`
（宿主服务）与清单的 `dsh.client.inject`（client 包），**漏声明都是冷启动才炸、
热挂载看着正常**。新写 client 半必须整抄一个冷启动正常样本的清单，不要凭空写。
