问题：孪生的**管理部分**是否涉及 `@dsh-external/dsh-super-injector`，那部分有没有 bug。

## 1. 结论先说

1. **孪生自己的代码零引用注入器**。全仓检索 `super-injector|dev_inject|dev_uninject|junction|dev_reload_package` 只命中两处**注释**（`lib/main.mjs:7`、`lib/impl.mjs:42`）。孪生不调 `dev_*` 工具、不读注入器状态、不写 patch。
2. **但孪生的挂载/启停（管理面）确实由注入器在内的四个写者共同决定**，这部分查出 5 个缺陷（F1–F5）+ 1 条观测口径问题（F6）。其中 F1 在本轮审计期间已被外部清理；F2/F3/F4 是机制性隐患，仍在；F5 在孪生侧、待用户决定处置。
3. **当前四个面一致**（本轮实测，`_dev/mount_health.mjs` 退出码 0）：单挂载源、loader 一条 active、junction 健康、私有停用表未屏蔽孪生。

## 4. 逐条发现

### F1 双挂载源：registry 与 bundle 抢同一包名 —— **本轮已被清理**

- **证据 A（源码）**：`restore()` 首行 `if (hasActiveEntry(e.name)) continue;`（`index.js` @326107 起）——已激活的包连「自动恢复」日志都不打。
- **证据 B（日志，证明两端都发生过）**：
  - 13:17:30.691 孪生已挂载（L2379）→ 13:17:30.817 起的自动恢复名单**没有**孪生（L2387–2391）；
  - 13:18:56.294 「自动恢复 dsh-liubian-twin」（L2439）→ 13:18:56.302 孪生挂载（L2440）。
  - 两者相隔 24 秒、同一个 profile 重载流程，说明「谁先手」不确定：bundle 先手时注入器跳过，注入器先手时它用 `loader.create` 建运行时 entry。
- **证据 C（观测）**：13:27:08 `dsh-liubian-twin (dsh-liubian-twin): Error: tool "_twin_note" is already registered`（L3452）。
- **影响（推断 + 注入器自述）**：注入器自己在源码注释里记载过这类失效模式——「运行时 loader.create（注入/自愈 fallback）产生幽灵 entry，与官方 bundles entry 并存 → include 对账把官方 entry 标 disabled → 官方清单 enabled=false、实际跑在幽灵上」（`index.js` @313129 起）。它的仲裁 `arbitrateOfficial()` 只筛 `String(e.options.name).includes("dsh-super-injector")`，**对第三方名字（如孪生）无仲裁**。C 是单次观测，不足以证明孪生必然双实例。
- **现状（本轮实测）**：`registry.json` 已无孪生条目（现只剩 novel-library-search / mail-report / notes 三条）；`dev_plugin_status` 显示 `[active] dsh-liubian-twin (dsh-liubian-twin)` 单条、**无 `[injected]` 标记** → 已回到单挂载源。清理动作非本会话所为（上一轮读取时该条目还在，`at=2026-10-01T03:37:16.567Z`）。

### F2 `dev_uninject_plugin` 对孪生是危险操作；`inject()` 早退不修 junction —— **机制仍在**

- **证据 A（源码，uninject 的破坏面）**：`uninject()` 卸 entry → 写 profile patch `- id: <短名> / disabled: true`（注释「阻断其 bundle patch 自装配」）→ `rmdirSync(linkDir)` + 「junction 已删除」（`index.js` @316517 起、@318200 起）。
- **证据 B（源码，inject 的顺序）**：`cleanupStaleEntries(pkgName)` → `if (hasActiveEntry(pkgName)) return "INFO: … 已激活运行，跳过注入"` → `purgeCache` → **之后才**检查/重建 junction（`index.js` @314516 起）。即：**早退发生在 junction 修复之前**。
- **证据 C（日志签名）**：06:34:54 `[hmr] config reload at …cordis.patch.yml failed` + `PackageOverlayNotFoundError: … cannot resolve package "dsh-liubian-twin" from the Desktop installation or active Profile`（L1055/L1056，06:37:54 复现于 L1084/L1085）。**同签名的其它插件**：kotatsu 03:47:32（L562）、embed 12:23:27（L1987）、embed 13:10:31（L2316）。
- **机制链（源码）**：解析失败 → `resolveOverlayPackage` 抛 `PackageOverlayNotFoundError`（`package-overlay-Ca250500.js:103-107`）；`loadRecoveryFilteredProfile` 对普通 bundle 的解析异常**直接 throw**（`profile-hhId3Pkk.js:692-717`）→ **整个 profile 重载失败**。要能解析，`profile/node_modules/<pkg>` 必须可读（`:39-42` 只接受 profile node_modules 内的候选）。
- **兜底**：junction 的自愈只在注入器 `apply` 时扫 `dependencies` 里 `link:` 项（`index.js` @326107 起 `healProfileLinks`），日志实例：11:24:07.998「断电自愈：重建 junction dsh-liubian-twin」（L1561）。
- **影响**：只要有人对孪生用 `dev_uninject_plugin` 且随后没能成功 inject（或误以为 `INFO: 已激活运行` 就是修好了），profile 的 junction 可能长期缺失 → 每次 patch/package.json 重载都失败（错落到 `[hmr]`，不看日志根本不知道）。
- **处置**：孪生侧写进文档 + 常态化体检（`mount_health.mjs` 第 ③ 项）。注入器侧属 基石（他已在本轮前给 `ctx.loader.internal?.loadCache` 加过守卫）。

### F3 Desktop 私有停用表：唯一「静默屏蔽」通道

- **证据（源码）**：`activeDesktopProfileLayers(profile, disabledBundles)` = `profile.layers.filter(layer => !(mutable && disabledBundles.has(layer.packageName)))`（`desktop-plugins-D2Dccc9D.js:357-359`，调用点 `profile-hhId3Pkk.js:950-952`）；读表 `readDesktopDisabledBundles`（`:201-205`）。
- **现状**：`state.json` 里 `profiles[desktop].disabledBundles = ["dsh-synapse"]`，**未**屏蔽孪生。
- **影响**：与 patch 的 `disabled` 行不同，这一条过滤发生在装配前、**日志无错**；是「孪生静默消失」链路里最隐蔽的一环（本会话未观测到孪生被它屏蔽）。
- **处置**：纳入体检第 ⑦ 项。

### F4 共享 `cordis.patch.yml` 被多方写，且键形不统一

- **证据（市场日志）**：`~/.dsh/profiles/desktop/.dsh-market/log.ndjson`
  - `{"event":"patch","detail":"disabled row dsh-liubian-twin in ~\\.dsh\\profiles\\desktop\\cordis.patch.yml"}`（2026-09-18T14:48:07.417Z 附近）
  - `{"event":"toggle","detail":"dsh-liubian-twin: patch layer disabled rows dsh-liubian-twin, 6c1f1dd2"}`（2026-09-18T14:48:07.428Z）
- **证据（日志噪声）**：patch 里 4 条 8 位哈希 id 行每次重载都会 `patch: entry "…" not found`（例：L1552–1554 为 `f2a70c2d` / `dsh-liubian-notes` / `4456ba9f`；`6c1f1dd2` 见 L236、L244、L266…）。
- **影响**：同一个启停语义被三套键、四个写者表达；哈希键无法从包名反推归属，残渣只增不减。
- **处置**：非孪生专有（`f2a70c2d`=kotatsu 时代、`4456ba9f`=notes、`5ddb9e87`=infra）。清理由 profile 所有者统一做；孪生侧只做只读提示。

### F5 孪生侧两个 `_dev` 脚本直接改写共享 patch —— **待用户确认处置**

- **证据（文件现状）**：`_dev/enable_twin.cjs` 会写入/摘除 `- id: dsh-liubian-twin / disabled: true`（含 `--close`）；`_dev/fix_patch_twin.py` 用正则删除 patch 里所有 `- id: dsh-liubian-twin` 行。
- **影响**：它们与 F4 的另外三个写者叠加，构成「谁最后写谁说了算」；`--close` 写下的块与 F2 的注入器残渣同类（`disabled` 阻断 bundle 自装配——该语义见 profile patch 自带注释，非本审计发明）。
- **处置**：**未动**。选项见 §6。

### F6 观测口径：注入器把时序假阴性计为 inject 失败

- **证据（源码）**：`const hostOk = hasActiveEntry(pkgName); … recordOp("inject", hostOk)`（`index.js` @316517 前后）——`loader.create` 之后立刻查 fiber 活跃度，未等待收敛。
- **证据（状态）**：`stats.json` 现为 `inject 300✓/97✗`，`lastFailures` 多条 `（无原因）`；`dev_plugin_status` 头部同样显示 `inject 300✓/97✗`。
- **影响**：97 不等于真实失败率（孪生曾占其中 1 条：11:37 那次注入其实成功了，见 L1672 的挂载行）。评估孪生管理面健康度时不能直接引用该数字。
