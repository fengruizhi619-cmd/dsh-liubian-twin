# 孪生重设计 v2：监督模块（2026-10-01，管理员定案：主体走 A + 独立监督对话）

管理员原话（14:4x）：主体走 A 路线；额外设计——在对话页「对话」与「轨迹」之间插一个叫**监督**的模块，也是对话形式，整体内容可完全照抄主对话；**它维护独立的上下文，不再与主智能体共享上下文**；需要审的上下文与对话以**消息方式**发给它，它给出监察意见。映射方式参考被炉，可问白泽。

---

## 1. 为什么这个设计同时解掉三个老问题

| 老问题 | v2 的解法 |
| --- | --- |
| 监察不审、反而续写执行侧（D0242） | 监督是**独立对话**：自己的系统提示（监察岗）+ 自己的历史回复确立角色；主对话内容是**发给它的资料消息**，不是"它自己的对话"——没有可续写的现场 |
| 烧 token（24k 字冷启动重发） | 上下文**只抄一次**（bootstrap），之后每轮审查只发**增量**（自上次以来的新消息 + 待审动作） |
| 缓存命中低 | 监督会话自身 append-only → 前缀持续命中（路线 A 的缓存洞察应用到监督会话自身）；审查发生在监督会话里=普通对话请求，形态可靠 |
| 成功率低 | 不再是冷启动单问+巨型文档；监督是一个**持续在岗的对话**，输出契约稳定；这正是压缩引擎/正常对话已被生产验证的形态 |

路线 A 的原则保留：**官方请求形态 + 前缀缓存经济**——只是共享对象从"每次重放主会话"改为"监督会话自身的持续前缀（一次照抄 + 之后增量）"。

## 2. 架构

```
主会话（被监督者，不动）
   │ ①bootstrap：deriveMessages() 全量照抄一次（cache-write 一次性成本）
   ▼
监督会话（独立 agent，宿主内真实会话）
   · system = 监察岗人设 + 判据摘要 + 输出契约（JSON 结论）
   · 内容 = 主对话照抄 + 历次监察意见（它自己的回复）
   │ ②每轮审查：孪生以消息方式投递「增量上下文 + 待审动作/文本」（被炉同款投递原语）
   │ ③监督回复监察意见 → 孪生读其最后一条 assistant 消息解析裁决
   ▼
闸门决策（allow / deny + 理由），超时按现行降级口径（fail-open）
```

- **创建**：主会话首次触发审查时创建监督 agent（带 agentOptions！——今天 `{{model}}` 事故的教训：resume/create 不带 options 就是静默坏会话）。
- **投递**：`agent.followup(...)`（被炉唤醒同款原语）把审查请求作为消息送进监督会话并唤醒。
- **回收**：主会话关闭/长期不活跃时跟随处置；主会话压缩不回传监督（两者上下文各自独立、允许分歧——管理员明确"独立上下文"）。
- **超限**：监督会话自身也会长大——它是宿主真实会话，compaction-basic 对它同样生效（自动获得缓存感知的压缩）。

## 3. UI：「对话 / 监督 / 轨迹」

桌面对话页现在的视图切换里，「轨迹」由 `@deepseek-ai/dsh-client-ui-trajectory`（client-ui 插件，`view.trajectory`）提供。目标是在它与「对话」之间插一个 **监督** 视图，渲染监督会话的对话（照抄对话的渲染形式）。

待白泽确认（他做过被炉面板的原生对话化改造）：
1. 对话页的视图切换有没有 client-ui 插件可挂的 slot？没有的话最小侵入做法是什么（kotatsu 面板路由 `/api/liubian-kotatsu` 那种自挂路由是否是既有先例）？
2. 监督会话是宿主真实会话——会不会自动出现在侧栏会话列表里造成干扰？如何在 UI 上只把它作为主会话的「监督」视图挂载？

## 4. 输出契约（监察意见）

保持与现行一致的裁决词约定（conform/deny + 理由 + 违反条目），但作为**监督对话里的正常回复**输出（末行 JSON 或结构化尾块）。文本闸门的纠正通道（`_twin_note`）与降级口径不变；监察意见同时落 jsonl 备份（现行落盘纪律不变）。

## 5. 成本模型（对照 v1）

| | v1 flatten | v2 监督模块 |
| --- | --- | --- |
| 每次审查输入 | 24k 字转录 + ~6k 字判据，全新前缀全价 | 增量消息 + 回复（前缀 cache-read 价） |
| 一次性成本 | 无 | bootstrap 照抄主对话一次（cache-write） |
| 形态 | 冷启动单问 + 巨型文档 | 持续在岗的对话（生产验证的形态） |
| 上下文保真 | 拍平 10 轮/24k 字、工具剔除 | 照抄全量 + 此后增量不丢 |

## 6. 风险与开放问题

1. **监督会话膨胀**：意见与增量不断累积 → 依赖宿主压缩；压缩后的监督"记忆"会粗化——可接受（它审的是当下动作，历史粗化不影响当下裁决）。
2. **裁决时延**：监督是真实 agent 回合（唤醒→回复），闸门要同步等——需要"投递→等它的新 assistant 消息→解析"的等待器 + 超时 fail-open（现行降级口径不变）。
3. **创建/resume 的坑**：必须带 agentOptions（`{{model}}` 事故）；会话 id 约定（如 `twin-supervise-<主会话id>`）；cwd/工作区继承。
4. **与旧 flatten 的共存/回退**：配置开关保留 v1 路径，v2 异常时一键回退。
5. **bootstrap 时机成本**：主会话已 604 回合时首次开监督 = 一次全量照抄（cache-write 全价）——可选"从压缩点开始抄"作为降档。

## 9. 白泽答复落定（房间 #197，16:48）——开放问题全部闭合

**9.1 UI：有公开槽，不自挂路由。** `conversation.view` 是**列表槽**：轨迹本身就是一条 entry（`dsh-client-ui-trajectory/lib/client.js` L8736：`slots.inject("conversation.view", () => slots.register({ name:"conversation.view", id:"trajectory", order:10, label, inject:(sessionId)=>… }))`）。孪生照抄注册 `{ name:"conversation.view", id:"twin-supervise", order:20, label:"监督", inject:(sid)=>该主会话有监督影子 }` → 得到「对话 / 监督 / 轨迹」并列页签，且 `inject` 可只在有影子的会话显示。注入器骨架白名单 KNOWN_SLOTS 本就含 `conversation.view`（预检放行；注入器退役后该预检随之消失，无依赖）。kotatsu 的 `sidebar.panellist + main` 是"整页视图"先例，**不适合**对话页内页签。→ UI 半在孪生包内实现。

**9.2 建监督会话：照官方 `dsh-api-session-controller` 的 `createOrAdopt` 抄，别自造签名。** cwd 是显式参数（主会话 cwd 在 `session.header.cwd`，被炉 join 工具就这么取）；**必须带 `agentOptions`**（今天 `{{model}}` 事故同源；resume 侧白泽已实测 `ctx.reflect.get('agentDefaultModel').currentSelection()` 可用）；`setup` 未验证。影子 id 约定 `twin-supervise-<主会话id>` 可行，但宿主是否强制 `session-<uuid>` 形状**未验证** → M1 先拿 `session-` 前缀试一次再定。

**9.3 投递与读回复。**
- 投递（followup 四要件）：`id`（randomUUID）/ `role:'user'` / `content` 数组 / `source.kind='plugin:dsh-liubian-twin'`（+ `form:'notice'` + `summary`）。**忙时宿主自动入队、空闲才唤醒**——不需要自己判 busy。
- agent 对象不在进程内 → 先 resume（**带 agentOptions**，否则就是今天的坏会话）。
- 读回复：订阅 `session/event`，过滤 `session.id === 监督会话id` 且 `type === 'assistant/message'`，文本在 `data.message.content[].text`（被炉输出映射同款）。
- ⚠ 自己投出去的消息会以 `agent/inbox/spliced` 事件出现在流里——**别把自己的投递误判成它的回复**。

**9.4 坑位清单（白泽原话归纳）。**
1. 影子会话会出现在用户会话列表——插件侧隐藏开关**未找到（未验证）**；
2. 影子会话照样吃压缩（阈值 0.7）→ bootstrap 的 deriveMessages 是起点、**之后只投增量，绝不反复灌全量**；
3. 别让影子会话进被炉成员簿（否则被炉输出映射会把它双向镜像）；
4. **绝不往主会话写任何消息**——步外 `assistant/message` 会永久弄坏该会话的压缩（血案 §3.3.5），最稳是根本不写；
5. 宿主重启后影子 agent 不在内存 → 走 resume 重建（带 agentOptions）。

**9.5 分工落定。** 宿主侧全归孪生；UI 半（`conversation.view` 注册）也在孪生包内（形状照 §9.1）。白泽可按需提供 `conversation.view` 注册最小样例或被炉 followup 代码摘录。

## 10. M1 实现清单（据 §9 定稿）

1. `twinV2` 开关（默认 false）+ 影子会话注册表（主会话 id → 影子 id/agent 句柄）；
2. `ensureShadow(mainAgent)`：create（`createOrAdopt` 形状：显式 cwd + agentOptions + setup[监察岗段，未验]）→ bootstrap 投递（deriveMessages 全量，作为第一批消息）；
3. `deliver(reviewRequest)`：followup 四要件 + 等待器（订阅 session/event → 监督会话新 assistant/message → 解析裁决；忽略 `agent/inbox/spliced`；超时 fail-open）；
4. UI：`conversation.view` 槽注册（`id:"twin-supervise"`、`order:20`、`inject` 按影子存在性显示），渲染影子会话消息（原生对话样式，参考被炉面板）；
5. 闸门接线：工具闸/文本闸在 `twinV2=true` 时走监督会话，`false` 走现行 v1 路径（一键回退）；
6. 桩测先行：投递形状 / 事件过滤（区分自己的投递与回复）/ 裁决解析 / 超时降级 / 开关回退。
